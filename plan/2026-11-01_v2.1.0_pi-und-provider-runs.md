# Plan: Version 2.1.0 – Pi- und Provider-Runs einheitlich anzeigen

## Ziel

`llmtop 2.1.0` zeigt gleichzeitig laufende und abgeschlossene Requests von

- **Pi Coding Agent** mit lokalen (z. B. Ollama) und Cloud-Modellen (z. B. ChatGPT/OpenAI),
- **Open WebUI** mit seinen konfigurierten Providern sowie
- den vorhandenen direkten **Ollama-CLI**-Aufrufen.

Jeder Run bleibt eindeutig einer Quelle und zusätzlich einem Provider zugeordnet. Alle aktiven Runs werden gespeichert und in der TUI über einen eigenen Scrollbereich erreichbar gemacht; kein Run wird mehr still auf drei Einträge begrenzt. Prompts, Antworten, Tool-Inhalte, Sessions und Zugangsdaten werden nie übertragen oder gespeichert.

## Recherche und Entscheidung

### Verifizierte Grundlage

1. Die offizielle Pi-Dokumentation beschreibt Erweiterungen als TypeScript-Module ohne separaten Build: Sie werden von Pi geladen, können Lifecycle-Events abonnieren und liegen für eine globale Installation unter `~/.pi/agent/extensions/`.
   Quelle: <https://pi.dev/docs/latest/extensions>
2. Pi liefert genau die benötigten stabilen Lebenszyklusgrenzen: `turn_start`/`turn_end` für einzelne Modellturns, `message_end` mit der autoritativen vollständigen Assistant-Nachricht sowie `agent_settled` für einen finalen Abbruch-/Idle-Zustand. `agent_end` ist ausdrücklich nicht final, weil Wiederholungen oder Folgeaktionen folgen können.
   Quelle: <https://pi.dev/docs/latest/extensions#lifecycle-overview>
3. Pi abstrahiert lokale und Cloud-Provider hinter derselben Session-/Event-Schnittstelle. Deshalb ist eine Pi-Erweiterung am Agenten die richtige Stelle; sie funktioniert für Ollama und ChatGPT/OpenAI gleichermaßen und benötigt keinen Provider-spezifischen Reverse Proxy.
   Quellen: <https://pi.dev/docs/latest/extensions>, <https://pi.dev/docs/latest/sdk>
4. Pi-Sitzungen enthalten potenziell sensible Inhalte. Der Adapter darf weder Sitzungsdateien lesen noch Prompt-/Antworttext als Ereignis senden.
   Quelle: <https://pi.dev/docs/latest/sessions>

### Gewählte einfachste Architektur

- Der vorhandene token-geschützte Collector `POST /v1/runs` und Schema 2 bleiben die **einzige** Schnittstelle. Es gibt keinen Proxy, keine Datenbank und keine Pi-/Node-Abhängigkeit in `llmtop`.
- Eine einzelne TypeScript-Datei wird als **globale Pi-Erweiterung** installiert. Projektlokale `.pi/extensions/` wären ungeeignet, weil sie Pi nur im jeweiligen vertrauenswürdigen Projekt erfassen würden.
- Die Erweiterung sendet best-effort per `fetch` mit kurzem Timeout. Ein ausgeschalteter Collector, Netzwerkfehler oder ein ungültiges Metrikfeld dürfen den Pi-Request nie beeinflussen.
- Open WebUI bleibt ein separater Adapter, nutzt aber dasselbe erweiterte Schema. So können Pi und WebUI parallel laufen und ihre Run-IDs kollidieren nicht.
- Das Pi-SDK wird nicht verwendet: Es wäre ein zusätzlicher Host für Pi und würde die bereits laufende CLI nicht instrumentieren. Die Erweiterung läuft direkt im bestehenden Pi-Prozess.

## Datenvertrag Schema 2.1

`llmtop_metrics.normalize_run()` wird abwärtskompatibel um die optionalen, kurzen Textfelder `provider` und `provider_model` erweitert:

```json
{
  "schema": 2,
  "event": "started|updated|completed|error|cancelled",
  "run_id": "uuid-v4",
  "source": "pi|open-webui|ollama-cli",
  "provider": "ollama|openai|anthropic|…",
  "model": "gpt-4.1|qwen3.5:4b",
  "started_at": "2026-11-01T12:00:00Z",
  "updated_at": "2026-11-01T12:00:02Z",
  "finished_at": "2026-11-01T12:00:08Z",
  "prompt_tokens": 42,
  "output_tokens": 125,
  "context_tokens": 167,
  "context_limit": 128000,
  "eval_duration_s": 5.2,
  "total_duration_s": 6.0
}
```

Regeln:

- `source` bleibt der Client; `provider` beschreibt die Modellherkunft. Fehlende Provider bleiben als `n/a` sichtbar, alte JSONL-Daten bleiben lesbar.
- `model` ist stets der von Pi/WebUI gemeldete Modellbezeichner. `provider_model` wird nur aufgenommen, falls Pi Modell-ID und Anzeigename getrennt liefert; sonst wird es nicht künstlich erzeugt.
- Token-, Cache-, Kosten- oder Dauerfelder werden nur gespeichert, wenn der Client sie explizit liefert. Fehlende Werte bleiben `n/a`; keine Schätzung.
- `source_run_id` kann weiter für eine nicht sensible technische Korrelation verwendet werden, wird aber nie aus Prompt, Chat-ID oder Session-Dateipfad gebildet.
- Begrenze `provider`, `provider_model` und `model` bei der Normalisierung auf sichere Texttypen und eine kleine Länge. Dadurch bleiben Collector und JSONL gegen ungewollt große Metadaten geschützt.

## Zielanzeige

### Aktuelle Runs

Der Bereich bleibt vor den geladenen Ollama-Modellen, erhält aber eine klarere Kennung:

```text
── Aktuelle Runs (4) ─────────────────────────────────────────
 Pi/OpenAI       gpt-4.1             running   Tokens: warten …
 Pi/Ollama       qwen3.5:4b          running   Tokens: warten …
 Open WebUI/…    claude-sonnet-…     completed Tokens: 1.2k …
```

- Quelle und Provider werden als `Pi/OpenAI`, `Pi/Ollama`, `Open WebUI/Ollama` usw. gezeigt. Damit sind gleichnamige Modelle verschiedener Anbieter unterscheidbar.
- Der bisherige Grenzwert `active_runs[:3]` entfällt. Alle aktiven sowie der letzte Abschluss jedes Clients verbleiben in `run.jsonl`.
- Da ein Terminal nicht beliebig viele Zeilen zeigen kann, wird der Abschnitt **scrollbar**: `a` schaltet den Fokus zwischen Aktuelle Runs und History; die vorhandenen Pfeil-, Bild- und Pos1/Ende-Tasten scrollen den fokussierten Bereich. Eine Positionszeile zeigt `Zeilen x–y von n`. Damit ist jeder Run erreichbar statt verworfen.
- In der 40×18-Ansicht bleiben Quelle/Provider, Modell und Status erhalten; Detailwerte stehen in der scrollbaren Großansicht und in `--once`.

### History und Snapshot

- Die History erhält bei ausreichender Breite eine Provider-Spalte direkt neben Quelle. Bei mittleren und schmalen Breiten wird die kombinierte Quelle `Pi/OpenAI` in der bestehenden Quellspalte ausgegeben, nicht still weggelassen.
- `--once` listet alle gegenwärtig aktiven Runs und die letzten zehn finalen Runs mit Quelle/Provider auf.
- **Geladene Modelle** bleiben korrekt als Ollama-spezifischer `/api/ps`-Bereich benannt. Cloud-Modelle erscheinen nicht fälschlich dort, sondern in Aktuelle Runs und History.

## Pi-Adapter

### Verteilung und Konfiguration

1. Der versionierte Quelladapter liegt unter `pi/llmtop_run_metrics.ts`, analog zu `open_webui/llmtop_run_metrics.py`; keine npm-Pakete und kein `package.json`.
2. Die README beschreibt die einmalige globale Installation nach `~/.pi/agent/extensions/llmtop_run_metrics.ts` und Pi-`/reload` beziehungsweise Neustart. Die Installation ist bewusst ein dokumentierter Kopiervorgang; `llmtop` schreibt nicht ungefragt in das Benutzerprofil.
3. Der Adapter liest ausschließlich `LLMTOP_COLLECTOR_URL` und `LLMTOP_COLLECTOR_TOKEN` aus der Prozessumgebung. Diese müssen in der Shell gesetzt sein, aus der Pi gestartet wird. Er sucht keine `.env`-Dateien anderer Projekte und greift nie auf Pi-Credentials zu.
4. Fehlen URL oder Token, registriert die Erweiterung nur einen geräuschlosen No-op. Das ermöglicht Pi weiterhin ohne Monitor-Konfiguration.

### Ereignisablauf

Vor dem eigentlichen Adaptercode wird gegen die lokal installierte Pi-Version ein kurzer API-Spike erstellt und mit `pi -e` geprüft. Er bestätigt die konkreten TypeScript-Typen für Modellkennung, Provider, Assistant-Usage, Turn-ID und Fehlerzustand; keine privaten oder geratenen Pi-Hooks verwenden.

Danach gilt:

1. Bei jedem einzelnen Modellturn erzeugt der Adapter eine UUID und sendet `started` mit `source: "pi"`, Modell, Provider und UTC-Zeit. Tool-Schleifen mit weiteren Modellturns ergeben bewusst weitere Runs.
2. Beim finalen Assistant-Ereignis ordnet der Adapter die explizite Usage diesem Turn zu und sendet `completed`. Er normalisiert nur bekannte Zähler (Eingabe, Ausgabe, Kontext, Dauer); unbekannte Usage-Felder werden ignoriert.
3. Ist ein Turn abgebrochen oder endet ohne Assistant-Abschluss, sendet der Adapter beim bestätigten finalen Agent-Zustand `cancelled` beziehungsweise `error`, ohne erfundene Metriken.
4. Die Zuordnung erfolgt ausschließlich über die vom geprüften Pi-Event bereitgestellte Turn-/Request-Kennung. Falls diese Kennung in der installierten API fehlt, ist der zulässige Fallback eine FIFO-Zuordnung innerhalb **eines Pi-Prozesses**; parallele unsicher zuordenbare Abschlüsse werden dann als separate offene Runs belassen, nie geraten zusammengeführt.
5. Das Senden läuft ohne `await` im kritischen Streampfad und hat maximal 500 ms Timeout. Fehler werden abgefangen und weder in die Modellantwort noch in den Pi-Kontext geschrieben.

## Open-WebUI-Anpassung

Der bestehende Filter darf nicht mehr nur `_is_ollama()` instrumentieren. Er wird zu einer kleinen Provider-Ermittlung erweitert:

- Für jedes verifizierte `__model__` sendet er `source: "open-webui"`, Modell und einen aus `owned_by`/`base_url` abgeleiteten Provider.
- Das vorhandene datensparsame `usage`-Parsing wird weiter benutzt. Provider ohne finale Usage liefern dennoch sichtbare Start-/End-/Fehlerzustände mit `n/a` statt gar nicht zu erscheinen.
- Die bestehende Behandlung mehrfacher Tool-/Fortsetzungsrunden, Heartbeats, Docker-Gateway und Valves bleibt unverändert.
- Der Adapter aktualisiert seine eigene Kopfmetadaten-Version auf 2.1.0; die API-Installation bleibt idempotent.

## Umsetzung in drei überprüfbaren Schritten

### 1. Gemeinsames Schema und Darstellung

Betroffene Dateien: `llmtop_metrics.py`, `llmtop_tui.py`, `llmtop.py`.

1. Optionales Provider-Feld validieren, persistieren und formatieren; vorhandene Schema-1/2-Daten unverändert lesen.
2. `source_label()` um eine kombinierte Quelle/Provider-Darstellung ergänzen und `--once` auf alle aktiven sowie zehn finale Runs erweitern.
3. Die Begrenzung auf drei aktuelle Runs entfernen, den aktiven Runbereich scrollbar machen und `a` als additive Fokus-Taste ergänzen. History-Bedienung bleibt kompatibel.
4. Die TUI-Hilfe, Kompaktansicht und Mindestgröße 40×18 anpassen.

**Abnahme:** Manuell erzeugte parallele Events `Pi/OpenAI`, `Pi/Ollama`, `Open WebUI/Ollama` und `Open WebUI/Anthropic` sind gleichzeitig in Live-Datei, TUI, `--once` und History unterscheidbar; kein vierter aktiver Run geht verloren.

### 2. Pi-Erweiterung

Betroffene Dateien: neu `pi/llmtop_run_metrics.ts`, `README.md`.

1. Lokale Pi-Version und exportierte Extension-Typen prüfen; einen Wegwerf-Adapter in `$TMPDIR` mit `pi -e` für lokale und Cloud-Modelle ausführen.
2. Den einzelnen, dependency-freien Adapter mit Start-, Erfolg-, Abbruch- und Fehlerereignissen implementieren.
3. Mit zwei gleichzeitig laufenden Pi-Prozessen testen: ein Ollama- und ein Cloud-Modell. Zusätzlich einen Tool-Loop und Collector-Ausfall prüfen.
4. Globale Installation nur nach explizitem Kopieren testen; danach Pi `/reload` und einen realen Prompt ausführen.

**Abnahme:** Beide Pi-Prozesse erscheinen gleichzeitig mit `source: pi`, unterschiedlichem Provider und Modell; der Collector-Ausfall verändert weder Pi-Ausgabe noch Exit-Code.

### 3. Open WebUI, Dokumentation und Release

Betroffene Dateien: `open_webui/llmtop_run_metrics.py`, `README.md`, `status.md`, `version.md`, `llmtop.py`.

1. Provider-neutrale Open-WebUI-Kennzeichnung implementieren und mit einem lokalen Ollama- sowie einem Cloud-Provider-Chat testen.
2. Einen Paralleltest mit mindestens einem WebUI- und zwei Pi-Runs durchführen; Live-Runs, finale JSONL-Deduplizierung, TUI-Scrollen und History prüfen.
3. `VERSION` auf `2.1.0` setzen sowie README, Status und Changelog synchronisieren. Die neue Taste, globale Pi-Installation, Umgebungsvariablen, Datenminimierung und Grenzen dokumentieren.
4. `git diff --check`, Syntaxcheck sowie die vorgeschriebenen `--version`, `--once` und `--once --no-nvidia`-Prüfungen ausführen. Anschließend den vollständigen 2.1.0-Stand committen, aber nicht taggen.

## Testmatrix

| Fall | Erwartung |
|---|---|
| Pi mit Ollama und Pi mit OpenAI parallel | zwei aktive `Pi/<Provider>`-Runs, unterschiedliche IDs, beide erreichbar |
| Pi-Tool-Loop | ein Run je Modellturn, keine falsche Zusammenführung |
| Pi-Abbruch/Providerfehler | final `cancelled`/`error`, keine erfundenen Tokens |
| Collector nicht erreichbar | Pi und WebUI antworten normal, nur Monitoring fehlt |
| WebUI und Pi gleichzeitig | Quelle, Provider und Modell bleiben in Live- und History-Datei getrennt |
| mehr als drei aktive Runs | alle persistiert und per aktivem Scrollbereich sichtbar |
| alte JSONL ohne Provider | lesbar, Anzeige `n/a`, keine Migration nötig |
| 40×18 | keine Überzeichnung; Quelle/Provider, Modell und Status sichtbar |
| Tokenlose Cloud-Antwort | sichtbarer finaler Run mit `n/a`, nicht verborgen |
| doppelter Abschluss | genau ein History-Eintrag pro `(source, run_id)` |

## Nichtziele und Grenzen

- Keine Anzeige von Cloud-Modellen im Bereich **Geladene Modelle**: dieser kann technisch nur Ollama `/api/ps` zeigen.
- Kein Mitschnitt von Prompts, Antworten, Sitzungen, Tool-Argumenten, API-Keys, Kosten oder vollständigen Provider-Rohantworten.
- Keine nachträgliche Erkennung fremder, nicht instrumentierter Pi-, WebUI- oder API-Prozesse.
- Keine neue Python-, npm- oder Systemabhängigkeit und kein automatisch gestarteter Hintergrunddienst außerhalb des bestehenden Collectors.
- Exakte Token- und Dauerwerte hängen von der jeweiligen Pi-/WebUI-Providerantwort ab. Die Anzeige behauptet bei fehlender Usage keine Genauigkeit.
